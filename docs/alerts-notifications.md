# Уведомления об ошибках на главной странице портала

Колокольчик 🔔 в шапке главной страницы портала (`sso-auth`), виден только
администраторам. Показывает активные проблемы, собранные `alerts_check.py`
по cron каждые 2 минуты (см. `setup_alerts_check_cron()` в `lib/services.sh`).

## Что проверяется

- **Сервисы** — `systemctl is-active` для всех systemd-юнитов панелей
  (`config.PANEL_UNITS`).
- **AMI** — живость через отдельного read-only AMI-пользователя
  `portalalerts` (Action: Login/Ping), не пересекается с AMI других панелей.
- **Диск** — свободное место на `/` ниже `DISK_FREE_PERCENT_THRESHOLD`
  (по умолчанию 10%).
- **HA** — только если на сервере настроен `/etc/atc-portal-ha.conf` (см.
  [[ha-cluster]]): keepalived запущен, VIP отвечает на ping, а на
  backup-узле — отставание репликации MariaDB не превышает
  `HA_REPLICATION_LAG_THRESHOLD` (30 сек).

## Как это устроено

У каждого узла — своя локальная БД `alerts_local.db` (не `sso.db`!
специально отдельный файл, исключённый из `sync_panels.sh`, чтобы push
с master не затирал алерты backup). Каждая проверка вызывает
`upsert_alert(key, ...)` при обнаруженной проблеме и `resolve_alert(key)` /
`resolve_missing(source, active_keys)`, когда проблема исчезла — активные
уведомления всегда отражают текущее состояние узла, история решённых
проблем остаётся в той же таблице (`resolved_at` не NULL).

## Объединение с соседнего узла (HA)

Раз пользователь всегда попадает на портал через VIP, а VIP в любой
момент указывает только на ОДИН физический узел — без объединения были
бы видны только алерты того узла, что сейчас активен. Поэтому:

- `sync_peer_alerts.sh` (генерируется в `lib/ha.sh` при настройке
  HA-кластера, работает **на обоих узлах**, не только на master) каждые
  2 минуты забирает копию `alerts_local.db` соседа в свой
  `peer_alerts.db`.
- `db.get_active_alerts()` при отображении портала читает **оба** файла
  (`alerts_local.db` + `peer_alerts.db`, если он существует) и
  показывает объединённый список — с меткой узла (`node`, hostname) у
  каждого уведомления.
- На инсталляциях без HA-кластера `peer_alerts.db` просто никогда не
  появляется — работает как раньше, только локальные алерты.

Задержка объединения — до ~2 минут (интервал `sync_peer_alerts.sh`),
этого достаточно для дашборда ошибок, не для оперативного мониторинга.

## Ручное снятие уведомлений

У каждого уведомления в списке — кнопка ✕ (скрыть одно), сверху списка —
«Очистить все». Это НЕ то же самое, что автоматический resolve в
`alerts_check.py`: снятие вручную скрывает уведомление, даже если
проблема ещё не устранена. Если она реально не устранена — `alerts_check.py`
на следующем цикле (~2 мин) создаст его заново, это ожидаемо.

- Уведомления **своего** узла снимаются напрямую в `alerts_local.db`.
- Уведомления **соседнего** узла (`node` в записи ≠ hostname этого сервера)
  снимаются через SSH на `PEER_IP` (тот же ключ, что уже используется
  `sync_panels.sh`/`sync_astdb.sh`) — правится РЕАЛЬНАЯ `alerts_local.db`
  соседа, а не только наша кэш-копия `peer_alerts.db`; локальная копия
  тоже обновляется сразу, не дожидаясь ближайшего цикла
  `sync_peer_alerts.sh`.
- Если сосед недоступен по SSH — снятие для его уведомлений завершится
  ошибкой (сообщение об этом), локальные уведомления снимаются независимо
  от этого.

## Автоочистка старых уведомлений

`db.cleanup_old_alerts()` — вызывается в конце каждого прогона
`alerts_check.py`, удаляет РЕШЁННЫЕ уведомления старше
`config.ALERTS_RETENTION_DAYS` (по умолчанию 30 дней). Активные
(`resolved_at IS NULL`) не удаляются никогда, независимо от возраста.

## Еженедельный тест HA-failover

`ha_failover_test.py` — по cron, воскресенье 4:00, только на узле с
`ROLE=backup`. Перезапускает keepalived НА СЕБЕ (не на master — реального
переключения ролей не вызывает, риск для звонков минимален) и проверяет,
что VIP не перехватился сюда неожиданно и остался достижим. Пишет в тот
же `alerts_local.db`, что и обычные проверки (`ha:failover-test`).

## Синхронизация fail2ban ignoreip между узлами

Изменения через панель обслуживания (`fail2ban_ignoreip.py`) best-effort
применяются и на соседнем узле через SSH (`PEER_IP` из
`/etc/atc-portal-ha.conf`) — правится реальный `jail.local` соседа, не
кэш-копия. Если сосед недоступен — локальное изменение всё равно
применяется, в интерфейсе показывается предупреждение.

## Восстановление бэкапа на backup-узле блокируется

`sync_panels.sh` каждые 3 минуты пушит с master на backup буквально всё,
что входит в резервную копию (все базы панелей в /opt/*, /etc/asterisk/
manager_custom.conf, /etc/nginx/conf.d/portal.conf) — только в одну
сторону. Восстановление архива на backup-узле поэтому молча откатывалось
бы обратно в течение 3 минут, без единого предупреждения. Панель
«Обслуживание» проверяет роль (`_read_ha_role()` читает
/etc/atc-portal-ha.conf) — restore на backup блокируется с понятным
сообщением, с явным чекбоксом «всё равно на backup» (`force=True`) для
намеренного обхода. На single-node инсталляциях (нет HA) проверка не
применяется.
